# Hono compatibility by import path

## Comparison sources and coverage

This document records the compatibility policy and is tracked in the repository and included in the distribution, rather than being a temporary report.
The unit of comparison is a public import path in the `hono` package, not a named function.
The comparison uses [Hono 4.13.18's package.json](https://github.com/honojs/hono/blob/f6fbaf0299c48eea9e656e03e2ffe7ac755e8823/package.json) and [Effect 4.1.4](https://github.com/Effect-TS/effect/tree/3e2030b43e86a60113f2f32671076ff3b1d84ce4).
The Hono comparison is pinned to commit `f6fbaf0299c48eea9e656e03e2ffe7ac755e8823`.

`package.json#exports` has 77 declarations: 76 fixed paths and one `./utils/*` pattern.
The [Hono build configuration](https://github.com/honojs/hono/blob/f6fbaf0299c48eea9e656e03e2ffe7ac755e8823/vite.config.ts) emits each `src/**/*.ts` file separately and excludes `*.test.ts` and `*.test.tsx`.
Under these rules, `./utils/*` expands to 28 existing modules.
The result is **76 + 28 = 104 concrete public import paths**, recorded in 104 rows below.
The wildcard also matches directory separators, so the list includes nested paths such as `hono/utils/jwt/jws`.
`hono/utils/jwt` and `hono/utils/jwt/index` resolve to the same implementation, but the tables list both because they are distinct import paths.
The tables also include type-only modules, deprecated adapters, and the root module.

| Category                                       | Concrete paths |
| ---------------------------------------------- | -------------: |
| Core, types, requests, clients, and validation |              9 |
| Built-in middleware                            |             27 |
| Helpers                                        |             14 |
| Routers                                        |              6 |
| JSX and DOM                                    |             10 |
| Runtime-specific adapters                      |              9 |
| Utilities and JWT re-exports                   |             29 |
| Total                                          |            104 |

External `@hono/*` packages are not public import paths of `hono` itself and do not count toward the 104 paths.
The pinned Hono `exports` does not declare `hono/package.json` or `hono/context`, so neither counts as a public path.

## Disposition criteria

- **Add**: This package supplies only general-purpose HTTP policies that neither Effect nor effront already provides.
- **Use Effect**: The listed Effect or Web standard API substantially meets the need, so this package does not add an equivalent wrapper.
- **Use effront**: The feature belongs to effront's application, rendering, serving, or runtime integration scope, so this package does not implement it.
- **Out of scope**: The feature is a Hono-specific implementation contract or an application-specific policy, and the row gives a specific reason for not adding it.

The absence of a dedicated middleware name does not establish a gap.
"Use Effect" does not guarantee identical function names, return values, options, or behavior details.
"Add" covers only the scope stated in the row and does not port all Hono options.
Unless stated otherwise, `Http*`, `Cookies`, `Etag`, `Headers`, `Mime`, `Url`, and `UrlParams` in the tables refer to namespace exports from `effect/http`.
`HttpApi*` and `OpenApi` come from `effect/http-api`.
`Effect`, `Context`, `Schema`, `Data`, `Clock`, `Layer`, `Logger`, `Stream`, and `Scope` come from `effect`.
`SecureRandom`, `Digest`, `Mac`, and `Signature` come from `effect/crypto`.
`Base64`, `Base64Url`, and `Sse` come from `effect/encoding`.
`Socket` comes from `effect/socket`, and `Path` refers to the `Path` export from `effect`.
The tables distinguish request instance fields from namespace functions.
This package does not implement features that effront covers, whether or not Effect has an equivalent.
[upstream-differences.md](./upstream-differences.md) records the reference commits and update policy.

## effront responsibilities and boundaries

The effront comparison uses [commit `3c8c55c8f99242b0c45c5a672fe3ea22f9e26614`](https://github.com/totto2727-org/effront/tree/3c8c55c8f99242b0c45c5a672fe3ea22f9e26614).
This package does not add a runtime dependency on effront.
Applications that need effront use it directly, and applications that need only HTTP policies use this package directly.

- Define applications with `Page`, `Routes`, `Layout`, `Component`, `Middleware`, `ServerFn`, and `make` returned by `Application.effront()`.
  These are not independent top-level exports.
- Applications, routes, layouts, middleware, Server Functions, React RSC and SSR, and browser hydration and navigation belong to `@effront/core` and `@effront/vite`.
- Leave Web Fetch and Workers integration to `@effront/core/workers` and `@effront/cloudflare`, and Node and Bun listeners to `@effront/server/node` and `@effront/server/bun`.
- Leave static serving of client and public assets, MIME detection, ranges, file ETags, and file 304 responses to `withAssets` from `@effront/server/assets` and its underlying `HttpStaticServer`.
- Leave stylesheet integration to effront's build and `@effront/tailwind` without adding a CSS-in-JS runtime.
- This package does not replace effront's HTML and Flight selection, the associated `Vary: Accept`, or its cache policy for private responses.
  Other APIs that need general Accept negotiation can use `Accepts`.
- `ResponseCache` is for separate GET APIs explicitly declared public, not for shared caching of effront's RSC, SSR, or Server Function responses.
- `ConditionalRequest` validators for arbitrary in-memory responses are distinct from effront and Effect validators for static files.
- effront's Server Functions already check Origin internally.
  This package does not port or reimplement that check.
  `Csrf` is a general-purpose policy for independent HTTP endpoints and does not re-expose effront's internal check through the same configuration API.
- `SecureHeaders` does not implement a renderer, nonce integration, or a Server Function runtime.
- Planned effront features do not count as implemented alternatives.
  This comparison does not claim that SSG or dedicated adapters for unsupported hosts already exist.

## Version boundaries and update checks

This package targets Effect 4's `effect/http` and `effect/http-api` and does not provide a compatibility layer for Effect 3's `@effect/platform`.
The Effect 3 comparison is for reference and uses commit `a67af3d016d40ad1f46a182c22e160c5346389c0`, which contains `effect` 3.22.4 and `@effect/platform` 0.97.3.
An Effect 4 feature is not evidence that Effect 3 has the same API.

When updating this document, get `package.json#exports` at the pinned commit and enumerate all fixed paths and all concrete wildcard paths that the build rules generate.
Compare the set against the first column of this document and verify that there are no missing, extra, or duplicate paths.
Check each row for a concrete counterpart or a reason for not adding it, and verify again that the package does not duplicate effront's implementation scope.
If the Hono comparison commit, effront reference commit, counts, or compatibility policy changes, update the README and the upstream record in the same commit.
